# 오늘의 CS 한 장

## 트래픽이 몰릴 때 DB보다 먼저 무너지는 건 설계다

- 캐시는 "빠르게 하는 옵션"이 아니라 "장애를 막는 경계선"이다
- 만료 시점을 설계하지 않으면 피크 시간에 장애를 예약하게 된다

> Note: 오늘 카드뉴스의 핵심 주장. 감정 공감 + 실무 리스크를 동시에 제시한다.

---

## 30초 상황 재현

- 점심 12시, 이벤트 배너 오픈
- 평소 대비 **40배** 요청 유입
- 핫키 캐시가 같은 시점에 만료
- 앱 서버가 동시에 DB로 재조회

> Note: 수치는 설명용 예시. 실데이터로 교체 가능하게 문장을 유지한다.

---

## 이 현상의 이름: 캐시 스탬피드

- 같은 키의 캐시가 비는 순간
- 다수 요청이 원본(DB/API)으로 한 번에 몰리는 현상
- 결과적으로 "동시 재계산 폭주"가 발생

> Note: 용어 정의는 1회만 하고 이후엔 쉬운 표현으로 반복한다.

# 왜 위험한가

## 장애 전파 5단계

1. 캐시 만료
2. 동시 캐시 미스 급증
3. DB 커넥션/쿼리 큐 포화
4. 전체 응답 지연
5. 연쇄 타임아웃과 에러율 상승

> Note: 원인과 결과가 이어지는 흐름으로 설명한다.

---

!!!캐시는 성능 기능이 아니라 장애 방어선이다

> Note: 메시지 고정 슬라이드. 발표 템포를 잠깐 늦추는 구간.

---

## 실패 패턴 3가지

- 모든 키에 동일 TTL 사용
- 캐시 미스 시 무제한 재시도
- 만료 직전 선제 갱신(warm-up) 미구현

> Note: "우리도 쉽게 빠지는 실수" 톤으로 전달한다.

# 실전 대응

## 대응 1. TTL 지터(Jitter)

- TTL에 랜덤 오프셋 추가 (`±10~20%`)
- 만료 시점을 분산해 동시 미스 완화
- 구현 비용 대비 즉시 효과가 큼

> Note: 가장 먼저 적용할 저비용/고효율 대책으로 강조한다.

---

## 대응 2. Single Flight

- 같은 키 재계산은 **동시에 1개만** 수행
- 나머지 요청은 결과 공유 또는 짧은 대기
- 애플리케이션/캐시 계층에서 락 또는 요청 병합 적용

> Note: 언어 종속 구현 대신 패턴 자체에 집중해 설명한다.

---

## 대응 3. Stale-While-Revalidate

- 만료 직후 짧게 **오래된 값 허용**
- 백그라운드에서 새 값 재계산
- 사용자 체감 지연과 장애 확률을 동시에 감소

> Note: 정확도와 안정성의 트레이드오프를 운영 관점으로 설명한다.

---

## 운영 지표 최소 세트

- 캐시 히트율/미스율
- DB active connection / slow query
- p95 응답시간, 타임아웃 비율
- 핫키별 요청량 상위 N개

> Note: "대응책 + 관측 지표"가 같이 있어야 운영 가능하다는 메시지.

# 배포 체크리스트

## 이벤트 전 10분 점검

- [ ] 핫키 목록 최신화
- [ ] TTL 지터 적용 확인
- [ ] 단일 재계산 보호 로직 점검
- [ ] SWR fallback 동작 확인
- [ ] 캐시 미스율/DB 커넥션 알람 임계치 점검

> Note: 마지막은 행동 가능한 체크리스트로 마무리한다.
